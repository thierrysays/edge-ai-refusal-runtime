# Audit, 21 August 2026

An external review at `v0.1.0`, immediately before publication. Method, findings
and what was done about each. Every figure was measured, not recalled.

Nothing found here was a break in a governance control. Everything found was in
the layer around them — the verifier's behaviour on input it did not expect, and
the absence of a machine-checked quality gate.

The adversarial pass is the substantive one. It is now
`tests/test_adversarial.py` and runs in CI.

## What the adversarial pass tried, and failed to do

**Signatures.** Transplanting signatures onto a modified card; signing with an
untrusted key to test for trust-on-first-use; repeating one key to fake a
quorum; `alg: "none"`; an empty signature list; backdating outside the key's
validity window; future-dating; editing `signed_at`; swapping `key_id` between
two otherwise-valid signatures. **All nine refused.**

The design reason they fail: the signed payload is not the card but
`{card_digest, key_id, signed_at}`, and roles are resolved from the trust store
at verification time rather than read from the envelope.

**The journal.** Reordering entries; deleting one from the middle; flipping a
`deny` to an `allow`; appending garbage; appending a two-megabyte line. **All
detected**, each naming the sequence number.

**Canonicalisation.** Key-order collisions, NaN and infinity, Unicode
normalisation collisions. **All handled**; Unicode is deliberately not
normalised, so visually identical strings with different code points do not
share a digest.

One adversarial test **passes on purpose**: `test_B4` asserts that a consistent
rewrite by the holder of the device key *verifies*. That is the limitation
[ADR 0007](adr/0007-external-anchoring-out-of-scope.md) accepts, and a test is
the only place a limitation stays honest. If it ever fails, the threat model
changed.

## Findings

### F-1 · The verifier crashed instead of refusing — **fixed**

`gea verify` pointed at a directory raised `IsADirectoryError`; pointed at a
binary file it raised `UnicodeDecodeError`. Both produced a Python traceback.

The exit code was still `1`, so CI was never wrong. The defect is what a person
sees: a tool whose entire output is *refusals with evidence* answering a wrong
path with a stack trace. An auditor cannot tell a crash from a finding.

Both now return a `VerificationReport` naming the reason.

### F-2 · An erased journal reported as verified — **fixed**

A 34-entry journal truncated to zero bytes produced:

```
journal verified: 0 entries, 0 checkpoint(s), head sha256:000000000000…
```

with exit code `0`, trust store present.

This is the sharpest finding. It sits close to the documented limitation that
post-checkpoint truncation is undetectable from the file alone, but it is worse
in kind: total erasure is the easiest possible attack, and the tool *affirmed*
the result. The README says a warn-and-continue gate "manufactures assurance,
which is worse than no gate"; saying `verified` about an empty file is the same
error in the verifier.

An empty journal is now a refusal, with the reason stated: an empty file and an
erased one are the same bytes, and telling them apart needs an external record
of the expected head — which is ADR 0007's territory, not something the verifier
can fix from inside.

### F-3 · No machine-checked quality gate — **fixed**

CI ran `pytest` and the demonstration. There was no lint configuration, no type
checking, no SAST, no dependency audit and no coverage floor. The repository's
own conventions were therefore preferences rather than rules, and preferences
drift.

Added: `ruff`, `mypy --strict`, `bandit`, `pip-audit` and a coverage gate, all
in `make qa` and all in a CI job that fails the build.

The coverage gate is **90 %**, not the 98 % the sibling `governed-edge-ai`
repository holds. Coverage here is 93 %. A gate set where the code actually is
fails when coverage *drops*, which is the only thing a gate is for; setting it
at a number the code does not meet would mean disabling it on day one. Raising
it is tracked work, not a number to assert in advance.

### F-4 · Nine strict-typing errors — **fixed**

`mypy --strict` reported nine, across `schema.py`, `marker.py`, `supervisor.py`,
`engine.py` and `admission.py`: three unannotated `confirm` methods, two
`bytes | bytearray` mismatches, three `Any` returns from functions declared to
return concrete types. None was a live bug. All fixed; `mypy --strict` is now
clean and enforced.

### F-5 · Three unused imports — **fixed**

In a repository whose subject is knowing exactly what is loaded, an unused
import is a defect rather than a style preference. `F` and `I` are now errors.

### F-6 · Two `bandit` Low findings — **justified in place**

Both are `random.Random(seed)` in `hal/sim.py`, drawing which parts are
defective and which inferences miss. Seeded and reproducible on purpose, never
key material. Now carry `# noqa: S311  # nosec B311` and a comment saying why,
so the next reader does not have to re-derive it.

## Not findings

Recorded so they are not re-raised:

- **`pip-audit` advisories in `pip` and `setuptools`.** Real, but in the runner
  image rather than this repository. CI now upgrades the build toolchain before
  auditing — fixing them rather than suppressing them.
- **`PTH`, `UP` and `E501` lint families.** Deliberately not enabled. They would
  churn working code without changing behaviour.
- **`hal/devices.py` at 75 % coverage.** The uncovered lines are
  `NotPortedError` paths for boards that have never been on a bench. They are
  covered when the port lands, not before.
